## 1. 结论

**重复产生在数据层，不在渲染层。** 同一个逻辑任务被**裁决了两次**（立项预裁决 + 执行裁决），而
`ledger.check()` 每次调用都会新建一条独立审批令牌，且 `pendingApprovals()` 不去重。

| 层 | 是否重复 | 证据 |
|---|---|---|
| 渲染层 | ❌ 干净 | `dsh-twin/src/client/dashboard.tsx:258-269` 单次 `dsh.approvals.map`；数据源唯一（`:92` `GET /dsh-ledger/approvals`） |
| 数据源 | ⚠ 只按状态过滤 | `dsh-ledger/src/ledger.ts:524-529` `filter(p => p.state === '待批准')`，无 (actionType,targetScope) 去重 |
| 产生点 | ✅ **根因** | `ledger.check()` 每次调用 `genId('A')` + 阻断时 `store.approvals.push(genId('P'))`（`:279-313`） |

## 2. 根因链（四步，逐步有据）

### 第 1 步 · `check()` 对同一动作不幂等（设计如此）

```ts
// dsh-ledger/src/ledger.ts:279-313
export function check(input: CheckInput, opts = {}): CheckResult {
  const record: LedgerRecord = { id: genId('A'), ... }      // 每次调用 → 新记录
  if (judgment.decision === '阻断') {
    approval = { id: genId('P'), recordId: record.id, ... }  // 每次阻断 → 新令牌
    store.approvals.push(approval)
  }
  store.records.push(record)
```
**这是正确的审计语义**——每次真实外发尝试都应留痕。问题不在 check 层。

### 第 2 步 · `adjudicate()` 每次调用都无条件 check（无复用）

```ts
// dsh-task-board/src/governance.ts:151-165
export function adjudicate(input: AdjudicateInput): GovernanceVerdict {
  if (!ledgerAvailable()) return adjudicateLocal(input)
  const result = ledger().check({ actionType, targetScope, levelHint, digest })  // 无 pending 复用
```
`adjudicate` 不查「本任务是否已有未决审批」，每次调用都产生新记录 + 新令牌。

### 第 3 步 · task-board 对同一逻辑任务调用两次 ✅ **根因所在**

| 时机 | 位置 | digest | 结果 |
|---|---|---|---|
| ① 立项预裁决 | `dsh-task-board/src/service.ts:222-233`（`createWithGovernance`） | `委托立项：<title>——<prompt 前80字>`（`:231`） | 阻断 → **P1** |
| ② 执行裁决 | `dsh-task-board/src/service.ts:246`（`run`） | `任务看板任务 <taskId>`（`governance.ts:158` 兜底，run 不传 digest） | 阻断 → **P2** |

**「对话内下单」是一次调用内连做两步**：

```ts
// dsh-task-board/src/tools.ts:188-195（task_delegate）
const t = await svc.createWithGovernance({ ... })   // → check #1 → P1
if (runNow) { const run = await svc.run(t.id, '手动') }  // → check #2 → P2
```
→ **单次 `task_delegate` 立即产生两条待批准**。这与「每个待审批都是两条」完全吻合。

`claim` 是第三个裁决点（`service.ts:353`，每次认领各一条）。

### 第 4 步 · 输出侧不去重

`pendingApprovals()`（`ledger.ts:524-529`）只 `filter(state==='待批准')`；`/dsh-ledger/approvals`
（`index.ts:298-301`）直接返回该数组。两条 P 各自独立 → 列表两个条目。

## 3. 为什么两条看起来「一模一样」

看板只渲染两个字段：

```tsx
// dsh-twin/src/client/dashboard.tsx:261-263
<span style={s.chip}>{a.actionType}</span>
<span style={s.itemText}>{a.targetScope}{a.expiresAt ? ` · 令牌有效期至 ...` : ''}</span>
```
而两条记录 **actionType / targetScope 必然相同**（同一任务同一动作），真正的差异在 `digest`
（`委托立项：…` vs `任务看板任务 TB-…`）——**digest 不在该渲染面**，故视觉完全无法区分。

### 现场自证方法（宿主侧）

读 `$DSH_HOME/dsh-ledger/ledger.json`，对 `records` 里 `status==='已阻断'` 的条目比对 `target.digest`：
出现成对的 `委托立项：…` 与 `任务看板任务 TB-…`（同 `target.scope`）即确诊本因。

## 4. 二阶症状（同因，可能已发生但未报告）

| # | 症状 | 机制 | 证据 |
|---|---|---|---|
| S1 | 批准一条后另一条仍在，需批准两次或等 3 分钟 | 两条 approval 状态独立；TTL 3 分钟（`ledger.ts:303`） | `ledger.ts:299-311` |
| S2 | 对话内批准后看板仍残留一条 | `task_approve` 只按 **run 的** `ledgerRecordId` 匹配 → 命中 P2，P1 留在原地 | `tools.ts:332` `find(p => p.recordId === blockedRun.ledgerRecordId)` |
| S3 | 账本审计面像「两次外发尝试」 | 同一动作两条 A 记录（digest 不同），事后审计易误判 | `ledger.ts:284-295` |

## 5. 系统性成因（比单点 bug 更重要）

**预裁决是后加的补丁，未与既有执行期裁决做消解。**

- 决策二（`docs/task-board-decisions.md`）原始设计：**执行前**过 ledger check 裁决 → 只有一次裁决。
- 安全审计 H1 补：立项时 `createWithGovernance` 预裁决（宪章 §5 补充记录：「立项即预裁决（L2+ 产生审批令牌，fail-closed）」）。
- 补丁**没有**消解两次裁决的重复，也**没有**统一创建路径：

| 创建路径 | 是否预裁决 | 证据 |
|---|---|---|
| 看板 UI `POST /action type=create` | ❌ 无（直接 `service.create`） | `index.ts:76-83` → `service.ts:512` |
| 对话内 `task_delegate` | ✅ 有 | `tools.ts:188` → `service.ts:222` |

→ 同一语义动作「创建任务」存在**两条治理语义不同的路径**：看板创建的任务账本中无立项记录（直到执行才落一条）；对话创建的任务落两条。

这是本问题的**结构性根因**：不是某行代码写错，而是「治理时机」在两个入口未统一，且新增裁决点未考虑幂等。

## 6. 修复方向（候选，未选定；须按流程走）

> 纪律：去重应发生在 **task-board 层**，不应削弱 `ledger.check` 的「每次裁决留痕」审计语义。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A（推荐）** 任务级令牌复用 | `createWithGovernance` 把 `approvalId` 存进 `TaskRecord`；`run` 前查该令牌是否仍 `待批准` → 命中则直接落「待审批」RunRecord，不再 check | 保留预裁决的 fail-closed 收益；账本只留一条；改动集中在 service | 需扩展 TaskRecord 字段；令牌过期（3 分钟）与长任务的时间窗需处理 |
| B 执行前查待批 | `run`/`claim` 前查 `pendingApprovals()` 按 (actionType,targetScope) 去重 → 命中则复用 | 不改数据模型 | 需从 ledger 取 pending（现有接口有 `pendingApprovals`） |
| C 取消预裁决 | 回到决策二原设计（仅执行期裁决） | 最简单 | 丢失「立项即拦截」的安全收益（对话内下单将不再预生成令牌） |
| D 输出侧折叠 | `pendingApprovals()` 或看板按 (actionType,targetScope) 折叠 | 症状消失 | **治标**：账本仍有重复记录，S2/S3 不解决 |

**附带必办**（无论选哪个）：统一两条创建路径的治理语义——要么看板 `create` 也走
`createWithGovernance`，要么明确放弃预裁决。否则同一动作在两入口行为持续分裂。
