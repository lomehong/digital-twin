# 成本/体验评审：分身心智运行时设计草案 v0.1

> 评审人视角：成本与主人体验。评审对象：`docs/mind-runtime-design.md`（v0.1，2026-09-18）。
> 参照底稿：headlong `thinkers/monolith/prompt.md`（函数菜单原文）、`design/monolith_backoff.md`（退避与成本原始推导）。

**结论：需修订后批准**

P1（心智本体，无渠道）大体可以直接做；但 §6.3 的 share/pending 只搬了机制没搬纪律，护栏（kill switch / spend cap / 降级）存在"吞掉对人的承诺"的漏洞，Q4 spend cap 没有给出可拍板的数。这三类问题写进 v0.2 只花半天，实施后回补则要动投递协议与速览契约，成本高得多。

## 0. 成本底账（后文引用）

### 0.1 一日自发唤醒次数（按设计 §5 默认参数：BASE=5s、FACTOR=2、CAP=300s、HOLD=3、THOUGHT_CAP=60s）

| 场景 | 估算式 | 唤醒次数/日 |
|---|---|---|
| 纯静默日（无互动、无真工作，无静音时段） | 24h × 3600/CAP = 24 × 12 | **288** |
| 纯静默日 + 8h 静音 | (24−8) × 12 | **192** |
| 常规互动日（8–15 段互动/真工作，每段把节奏拉回 level 0，连续思考段速率远高于 12/时；每段跑干后约 21 次空唤醒、15–20 分钟重新退避到稳态） | 288 + 连续思考段增量 | **≈300–600** |
| 反刍日上限（分身持续只产出 thought，按 THOUGHT_CAP=60s 触底） | 24h × 3600/60 | **1440** |

### 0.2 每次唤醒的成本 C_wake

token 估算依据 headlong 菜单提示词体量外推：本地化菜单提示词 ≈1.5–2K + 人格卡/路由信号/最近流 ≈1–3K + 工具 schema（memory 读写 + task_delegate + web）≈1–2K → **输入 ≈4–7K（取 5K）**；决策 + 时间线步骤 + FINAL 交接棒 → **输出 ≈0.2–0.8K（取 0.5K）**。

**核心公式**：

```
C_wake = T_in × P_in + T_out × P_out          （无缓存）
       = T_hit × P_hit + T_miss × P_in + T_out × P_out   （开提示词缓存，T_hit≈4K）
$/日  ≈ [ (24−Q)×3600/CAP + Σ各互动段的连续思考/下坡唤醒 + R ] × C_wake
上限   = 24h × 3600/THOUGHT_CAP × C_wake      （反刍失控日）
```

（Q=静音小时数，R=反应性唤醒数——反应性不受限但必须**计量**。单价以 2026-09 常见官价为示例，实施时须按当期价复核。）

| 模型档 | 假设单价 in/out（$/M tok） | C_wake | 闲置 $/时（12 次） | 闲置 $/日（288 次） | +8h 静音（192 次） | 反刍失控 $/日（1440 次） |
|---|---|---|---|---|---|---|
| deepseek 级 | 0.28 / 0.42 | ≈$0.0016 | $0.019 | **$0.46** | $0.31 | $2.3 |
| deepseek 级 + 缓存（80% 命中） | 0.028 命中 / 0.28 / 0.42 | ≈$0.0006 | $0.007 | **$0.18** | $0.12 | $0.9 |
| Claude Sonnet 级 | 3 / 15 | ≈$0.023 | $0.27 | **$6.5** | $4.3 | $32 |
| Claude 级 + 提示词缓存 | 0.30 读 / 3 / 15 | ≈$0.012 | $0.14 | **$3.4** | $2.3 | $17 |

**要点**：设计 §5 引用的"默认节奏 $1–2/小时"是 headlong（Claude 级模型、互动密集场景）实测的照搬。对 deepseek 级模型，闲置成本实为 **$0.01–0.02/小时**，低了两个数量级；对 Claude 级且未用提示词缓存才与之同量级。成本护栏必须按**已配置模型的单价**推导，不能引用一个普适常数。

## 阻断项（Blockers）

### B1 share 防噪音只有一句提示词，缺运行时机制——不补上分身就是骚扰泵

**依据**：headlong 的教训恰恰是**提示词纪律不可信，必须在机制层强制**。`prompt.md` L14 的 `chat send` "refuses an exact repeat within a day" 是工具的硬拒绝，不是劝说的产物； wakes 上下文里还有专门的 "Sent in the last 24h" 区（delivered/pending=已说过；FAILED=从未送达、修好地址后重发）。设计 §4.2 只有"`share`（有新东西找具体的人）"一句，§6.3 只有销账协议，`deliver` 的 `Promise<void>` 没有投递状态语义。LLM 非确定性 + 每次唤醒独立 run 的结构，意味着纯靠提示词的"别说重复的话"**必然**失守，且失守的方式（凌晨给主人重发昨天的结论）正是骚扰。

**必须搬进设计的清单**（缺一即骚扰泵化）：
1. **24h 重复拒绝（机制层）**：deliver 实现里做 recipient + 内容指纹（hash）的 24h 去重，重复直接拒绝并记 `error` 步骤；不依赖提示词自觉。
2. **投递状态 + FAILED 语义**：`message_out` 记录 `sent / failed / pending_delivery`；failed ≠ 已说，显式可重发；唤醒上下文注入"最近 24h 已发"摘要，供 share 决策去重。
3. **"新信息才 share"完整规范**（不只是"有新东西"）：永不 status ping、永不重复回答、永不对同一发现发第二次追发；同时保留反向纪律——克制不等于沉默，有新东西就该说（prompt.md L22 "don't repeat and don't dump — it does not mean stay silent"），防止矫枉过正成哑巴。
4. **一次请求一次交付**：深工办不成，"办不成 + 原因"本身就是那次交付（prompt.md L22 "if the work cannot be done, deliver that as the answer"）——这条直接决定 B2 的兜底话术。
5. **对人的消息写作规范**（见应改项 S5 的中文适配表）。

### B2 pending 的"人的等待体验"缺失，且护栏路径会吞单——"承诺永不悬空"在 v0.1 不成立

**依据**：§6.3 只写了时间线侧的销账协议。但从人的视角：快速回复说了"我去办"之后，等多久？超时怎么办？按下 kill switch 的瞬间，一个正在等待的朋友会怎样？逐条检查发现承诺会悬空的路径至少有四条：kill switch（调度器停）、spend cap 硬顶（条文只说"反应性保留"，未明确 pending 处理是否算反应性）、watchdog 假死窗口、deliver 失败。任何一条悬空 = 分身在现实里欠了一个人一句回复且永不还。

**必须补进 §6.3 的协议**（人的时间线）：
- **t=0**：快速回复（≤数秒）必须带预期话术："收到，我去办，大概 X 分钟内回你"。X 按档位给（快 ≤2 分 / 中 ≤10 分 / 慢 >10 分会再来说一声）。设计需写明这句由谁产出：建议渠道固定模板（responder 生成则要在契约里约束它必须含时长承诺）。
- **t=X 交付**：结论先行；办不成也要交付（B1 第 4 条）；不叙机器内幕（"我唤醒了三次"禁止）。
- **t=X+超时**（建议默认 15 分钟，可配）：渠道侧兜底发一条"这事卡住了，恢复后我会继续/暂时办不了"，pending 标记 stale、速览红色、告警日志（对齐 G5"失败显式告警不静默"）。
- **护栏不吞单**（写死在 §5 与 §6.3）：kill switch 触发时若存在未销账 pending，必须先逐条处置——可交付的交付，不可交付的由渠道发"分身已暂停，此请求待恢复处理"；SPEND_CAP 硬顶条目明确"反应性保留"**包含 pending 的处理与交付**；降级路径（§6.2 im-channel 缺席）下渠道不注入 pending，行为与今天一致，无此问题——把这句也写明，闭合所有路径。

### B3 spend cap 没有默认值、没有推导公式、没有软硬两级（Q4 不能再空着）

**依据**：§5 的唯一成本硬闸在 Q4 里留空（"如 $X/日，实施时按模型定价定"）。而 §0.1/§0.2 显示成本横跨两个数量级（deepseek 闲置 $0.18/日 vs Claude 级反刍失控 $32/日），"实施时再定"等于没有护栏上线。且单一硬顶的语义太粗：触顶即哑火半天，主人体验是"分身上午还活着下午就死了"。

**具体建议（可直接写入 Q4）**：
- **推导公式**：`cap = 2–3 × 静音后稳态日成本`，即 `2–3 × (24−Q) × (3600/CAP) × C_wake`，向上取整到方便的数。
- **默认数**：deepseek 级 **$1/日**（稳态 $0.2–0.5 的 2–3 倍，宁小勿大）；Claude Sonnet 级 **$5/日**（稳态 $2.3–3.4，配软顶后日常够用，深工日触软顶自动降档而非硬停）。
- **两级语义**：**软顶 80%**——自发唤醒降级（切快模型，见 S2，或 CAP 翻倍），反应性与 pending 全保留；**硬顶 100%**——自发唤醒停、反应性与 pending 保留、速览红条 + 告警。
- **计量口径**：自然日、按主人时区零点重置（与 QUIET_HOURS 同一个时区字段）；反应性计费照记但不受限，速览分列"自发/反应"两栏，让主人看到真实的全口径日消耗。

## 应改项（Should）

### S1 成本预期改写为公式表，删掉"$1–2/小时"的普适表述

**依据**：§5"成本预期：对齐 headlong 实测量级（默认节奏 $1–2/小时）"。如 §0.2 所示，该数只在 Claude 级未充分缓存时成立；deepseek 级实际 $0.01–0.02/时。照搬会让主人在低档模型上白白把 cap 定大 10 倍（护栏失效），或在高档模型上被"$1–2"误导而把 cap 定小 3 倍（天天触顶）。
**建议**：§5 直接嵌 §0.1/§0.2 的两张表 + 公式，注明"单价实施时按当期官价代入"；验收标准从"成本符合预算"改为"实测 $/日 落在公式预测区间 ±50% 内"。

### S2 自发唤醒的模型档位：深退避档默认切快模型（Q2 的成本面）

**依据**：Q2 建议"决策用主模型"，headlong 原推导把"给自发唤醒降档模型"列为第二杠杆（monolith_backoff.md "Optional second lever"）。闲置唤醒的期望价值低（多数以 idle/thought 收场），却按主模型全价计费：Claude 级上闲置一天 $3.4–6.5，其中大部分花在"想了一步然后休息"上。
**建议**：level ≥ 3（delay ≥ 20s）的自发唤醒默认用快模型（deepseek 级本来就便宜，可不开）；软顶触顶时无条件切快模型。粗账：Claude 级闲置日成本 $3.4 → 快模型承担深档后约 **$0.7–1/日**，省 70–80%，而"主人一说话就全模型"的响应质量零损失。

### S3 THOUGHT_CAP=60s 是无理由照搬，它定义了最坏自发速率

**依据**：headlong 把纯 thought 限定在 60s 触底，是为了修"反刍全速空转"的 bug（写作'nothing changed'曾被当成工作）——60s 是 headlong 旧 60s cap 的遗迹，不是推导值。设计照抄后，最坏自发速率 = 60 次/时 = 1440 次/日：deepseek $0.9–2.3/日尚可接受，Claude 级 $17–32/日，两个硬顶日就烧穿。
**建议**：要么默认 `THOUGHT_CAP = CAP`（纯 thought 即空唤醒，最简单，反刍上限回到 288 次/日），要么保留 60s 但在 §5 写明理由（要更活的心跳）并让主人知情。建议前者，理由是 inner life 的"活性"由互动日保证，静默日没人为 60 秒一次的独白付费。

### S4 QUIET_HOURS 需要时区语义、默认开启、旅行策略，并管住 share

**依据**：§5 只写"QUIET_HOURS = 可配"。三个缺口：(a) 时区未定义——host 时区在主人旅行时是错的；(b) 无默认值——默认不开则 0:00–7:00 的 96 次自发唤醒（占比 1/3）全发生在主人睡觉时；(c) 静音只管"自发唤醒"，不管 message_out——凌晨三点的 share 对人是噪音，哪怕它对系统是"反应性"。
**建议**：
- 配置形如 `"23:00-07:00@Asia/Shanghai"`，**显式 IANA 时区字段**，默认取主人 profile（dsh-twin 人格卡或 master 配置）的时区，缺省回退 host 时区并在速览显示"当前生效时区"。
- **默认开启**（23:00–07:00）：闲置日成本 288→192 次（省 1/3），噪声同步减 1/3。
- **旅行**：不做自动地理检测（隐私 + 误判），插件页给一键"旅行切换"——改时区字段或临时关静音，生效时区在速览常显。最坏情形（忘了切）只是主人的白天多几条自发消息，可接受。
- **静音期 share 缓发**：非紧急 message_out 在静音期入队、静音结束后投递；**pending 交付豁免**（有人在等，永远立即送）。

### S5 headlong 消息写作规范必须中文重导，不能直译

**依据**：prompt.md L24–39 的规范是英文 IM 语境的产物，其中多条直译后会失真或失效；而"结果先行、不叙机器、不吹捧开头"这些与语言无关的骨架必须原样保留。逐条对照：

| headlong 原文（L30–38） | 中文适配建议 |
|---|---|
| No dashes of any kind | 不必一刀切禁标点：禁的是把"——"当万能连接词（中文 AI 腔重灾区），罕用即可；另禁"~"结尾 |
| No bold / headers / bullets / code | **保留且更硬**：微信纯文本渠道 Markdown 渲染成星号原文；飞书卡片渠道可按渠道放宽（规范标注"渠道相关"） |
| Don't open by praising / agreeing | **保留并点名中文重灾区**："好问题！""您说得对""没错，"一律禁 |
| Don't restate their question | 保留 |
| No ending question unless needed | 保留 |
| No machinery narration（wakes/trajectory/responder…） | 保留，清单本地化：唤醒、时间线、心智、responder、函数菜单 |
| No filler / sign-off / offers | 保留并点名："希望对你有帮助""有任何问题随时找我""以上" |
| Everyday words, no synonym-swap（no delve/robust/leverage） | 保留结构，黑名单换中文 AI 腔：赋能、抓手、底层逻辑、颗粒度、痛点、拉通；不刻意换近义词照抄 |
| 结果先行、1–2 句平话；未验证就说未验证 | 保留（语言无关） |
| heredoc/双引号转义教训（L39） | **无需搬**：dsh-mind 的 message_out 走 timeline 结构化字段不经 shell，这类事故在设计里天然不存在——提示词里删去此条即可 |

**边界**：你/您、emoji、语气词（呢/啦/哦）等"加法"规范不进全局规范，交给人格卡（dsh-twin）——规范只管减法，人格管口吻。

### S6 速览（§3.2）信息架构具体化：五区块，按主人的决策频率排序

**依据**：§3.2 只写"最近 N 步 + 当前状态 + spend 统计"。主人打开这页的真实问题是三个：它在烧钱吗？它欠谁的话？怎么叫停？据此排信息架构：

```
┌─ 分身心智 ──────────────────────────────────────────┐
│ ● 运行中 · 下次自发唤醒 3 分后 · 退避档 7/300s        │
│ 今日成本 $0.34 / $5 ▓▓░░░░░░░░ 7%（自发 41 / 反应 12）│ ← 80% 处画软顶刻度
│ [⏸ 暂停]  （kill switch，一键停，恢复一键；状态持久化）  │
├─ 等它办的事（pending）───────────────────────────────┤
│ ! 张三 · 周报数据 · 已等 22 分 · 超时   [催办][销账]    │
│ ✓ 李四 · 查日程 · 8 分前已回复                         │
├─ 最近动态（20 步，wake 行默认折叠）───────────────────┤
│ 10:42 message_out → 群A  ✓已送达                      │
│ 10:12 message_out → 张三  ✗失败  [重发]                │
│ 09:58 thought "……"（折叠）                            │
├─ 今日对外发言（24h sent）─────────────────────────────┤
│ 3 条：张三×1 · 群A×2  [查看]                           │
└─────────────────────────────────────────────────────┘
```

要点：① 状态行与成本行合并置顶（运行态、下次唤醒倒计时、退避档、$/日 已用/上限）；② pending 列表是"承诺永不悬空"的可视化（B2），带超时红色与销账/催办操作；③ kill switch 在首屏（§5 已有，落实为按钮）；④ 时间线 message_out 必须带投递状态（B1 第 2 条），wake 步骤默认折叠（headlong 明确 wake 是机器步、排除出视图）；⑤ "24h 已发"列表同时是防噪音纪律的观测窗——主人一眼看出分身今天对外聒噪与否。

### S7 反应性风暴缺最后一道闸：spend cap 触顶后的反应性降级

**依据**：G3 规定反应性永不限速——正确，但代价是无上限：被拉进活跃群、两台分身互聊、渠道故障循环注入，反应性唤醒本身就是大开销（Claude 级一段 30 条消息的热聊 ≈ $1–3，纯 5K/0.5K 估算下限），且 spend cap 条文对反应性完全无动作。
**建议**：反应性**永不停**，但 spend cap 硬顶后反应性唤醒可降快模型 + 明确告警主人"今日反应性消耗异常（N 次，来源 channel=X）"。计量分列（B3）让主人能定位风暴源；是否加"同源消息频控"属架构问题，越界不展开，只留一句：速览的反应性计数按渠道分列即可支撑日后判断。

## 建议（Nice）

- **N1 share-nudge 机制**：headlong 每 12 次自发唤醒注入一条"考虑 share"的路由提示（`MONOLITH_SHARE_HINT_EVERY`，0=关），防止分身过度内向。300s cap 下≈每小时一催，防噪音靠 B1 的机制层去重兜底。建议 P2 作为可配项引入，默认开。
- **N2 长期暂停提醒**：kill switch 挂起超 24h，IM 侧给主人一条"分身已暂停 X 天"。防止主人忘关后分身"无声死亡"数日（对主人是体验问题：以为它在，其实不在）。
- **N3 watchdog 阈值**：X 应 ≥ 2×CAP 且 ≥ 15 分钟（默认 300s 时取 15 分钟），合成唤醒在时间线里记 `reason=watchdog`，与真实 idle 可区分——否则排障时分不清"它想歇着"和"它死了"。
- **N4 每唤醒 token 预算**：给唤醒上下文设 token 预算（如输入 ≤8K），P3 记忆金字塔上线后 recall 结果按预算裁剪。C_wake 是 §0.2 一切公式的乘数，防止它随时间悄悄翻倍；速览加"每唤醒平均成本"一周趋势线。
- **N5 退避参数进速览**：BASE/FACTOR/CAP/HOLD/THOUGHT_CAP 做成速览里的可调项（带默认值复位），主人不用去改 config.json——成本调节的最后一米是"调的时候不肉疼"。
